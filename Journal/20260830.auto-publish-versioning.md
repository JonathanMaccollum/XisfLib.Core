# 2026-08-30 — Switch to auto-publish versioning (VersionPrefix 1.2)

Yesterday's ZstdSharp.Port bump landed on main without a version edit or tag, so nothing was
published and `Publish-Desktop.ps1`'s sibling gate blocked the desktop release: HEAD ahead of the
newest published v1.1.3. Root cause is the release construct, not the commit — this library's
remaining change profile is almost entirely patch-level maintenance, so the manual version+tag
ceremony was pure bookkeeping with a silent-drift failure mode (the same class that shipped desktop
v0.141 without its PreProcessing fix).

Adopted the `EigenFrame.PreProcessing` construct:

- `XisfLib.Core.csproj`: `<Version>1.1.3</Version>` → `<VersionPrefix>1.2</VersionPrefix>`, the only
  maintained version line, touched only for a deliberate new minor/major. 1.2 (not 1.1) because the
  patch comes from `github.run_number`, which is small for this workflow — a 1.1.<run> could sort at
  or below the already-published 1.1.3.
- `.github/workflows/publish.yml`: trigger moved from `v*` tags to push-to-main (+
  `workflow_dispatch`), version computed as `VersionPrefix.<run_number>`, published version tagged
  back to the repo. `paths-ignore` on `Journal/**` and `README.md` so docs-only pushes don't mint a
  release. Kept this repo's own NuGet trusted-publishing OIDC auth and .NET 8 — only the
  trigger/versioning moved.

Consumers: the three `1.1.*` floats widened to `1.*` (`XisfPrep`, `EigenFrame.Desktop` +
`Tests`) so they pick up 1.2.x; `EigenFrame.Worker` keeps its exact `1.1.3` pin deliberately — its
deploy path is ungated, so it moves versions only by explicit edit.

First push of this to main publishes and tags `1.2.<n>` from that HEAD, which is what clears the
desktop publish gate.

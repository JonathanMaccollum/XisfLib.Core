# Rev 1 TDD wave 2 — scaffold + red/green ledger

Wave 2 of the three-wave TDD effort defined in `20260919.rev1-implementation-contract.md` (read that
plus Amendment 1 first; gap list in `20260919.xisf-1.0-revision1-conformance-assessment.md`). Wave 1
authored the 12 test files without ever compiling them. This entry records the scrutiny pass, the
compile-enabling scaffold, the infra items, and the measured red/green ledger that wave 3 works from.

No contract logic was implemented. Every library change here is either a new type/member the tests
name, or one of the infra items the contract lists.

## The one mismatch

`AstrometricCarriageTests.UnrecognizedSolutionPropertyId_RidesAlong` — declared **green**, measured
**red**. Classification **(b) declared expectation wrong**; the test is sound, the header comment was
not. The assertion is about a String property with an unknown identifier, which wave 1 reasoned would
round-trip today — but the test reaches it via `RoundTripSolutionImage()`, which writes the *whole*
solution property set, so it dies on the same
`NotSupportedException: Property type XisfVectorProperty is not yet supported for serialization`
(`XmlSerializer.cs:496`) as every other member of that file. It is gated on contract item 6 exactly
like its siblings.

Resolution: the file's header block was edited to move that name into EXPECTED-RED, keeping its
original §11.5.3.7.7 rationale and recording why wave 1's placement was wrong. No assertion changed.
This is the only test-source edit wave 2 made.

**No unexpected greens.** Every test wave 1 declared red is red, and every test declared green is
green — so no red test is passing for the wrong reason, and nothing needed strengthening. Three
greens do pass *vacuously* today and wave 3 must keep them honest; they are listed under "What wave 3
must know" below.

## Scrutiny pass (phase 1)

Every test file was read against the contract + Amendment 1 and, where cited, against
`XisfLib\docs\XisfSpecification 1.0 Revision 1.md`. Checks performed and their outcome:

- **Spec citations verified against the spec text**, not taken on trust: Table 3 scalar alternate
  names (`Byte`/`Short`/`UShort`/`Int`/`UInt`/`Float`/`Double`), Table 7 vector and Table 8 matrix
  alternates (`ByteArray`/`IVector`/`UIVector`/`Vector`, `ByteMatrix`/`IMatrix`/`UIMatrix`/`Matrix`),
  the §8.3.3 non-finite grammar `NaN | [-+]Inf | -?nan | -?inf`, §8.3.4 Boolean `1`/`0`, the §8.4.1
  single-colon identifier regex (and that ValidationTests' accept/reject examples are the spec's own
  examples), §11.1.6 "a String Property shall not have a value attribute", §11.1.8/§11.1.9 empty
  vector/matrix = zero-length inline block with empty character contents, and the §11.4.2
  newline-separated (Authors/BibliographicReferences/Contributors/RelatedResources) vs
  comma-separated (Keywords/Languages/CompressionCodecs/ChecksumAlgorithms) split. All test
  assertions match the spec. No spec contradictions found.
- **Amendment conformance**: no test contradicts A1 (no test asserts a String `value` attribute is
  emitted), A3 (`Emit_NonShuffledCodec_CompressionAttributeOmitsItemSize` asserts exactly two
  components, its `+sh` sibling exactly three), A6–A8 naming, or A9 (validation is reached through
  the public `XisfWriter.Validate`, so no `InternalsVisibleTo` is needed).
- **The flagged layout conflict does not exist.** `TestKit.BuildMonolithic` pads the declared header
  so block 0 starts at `AlignedBase(headerLength)` and later blocks follow contiguously, and it
  appends nothing after the last block — so the file ends at the last block and
  `file.Length - blob.Length == blockBase`, which is precisely the fixed point
  `NamespaceTests.HeaderProbe.BuildAttached` iterates to. Both helpers' assumptions hold
  simultaneously for every fixture in the suite (`HeaderProbe` is only ever used with one blob).
- **Duplicate test names**: none, across all 12 files.
- **TestKit usage**: every call site matches `TestKit.cs` as written. `TestKit.PropertyValue`'s trim
  is only ever used on assertions where trimming is immaterial; the two tests that care about
  significant whitespace (`TermsString_SerializedAsCharacterContent`,
  `NewlineSeparatedListFields_EmitNewlineSeparatedValue`) read `XElement.Value` directly or tolerate
  the trim.
- **Third-party API shapes used by tests** (`ZstdSharp.Decompressor.Unwrap(byte[], byte[], int)`,
  `K4os.Compression.LZ4.LZ4Codec.Decode`) resolve transitively through the `ProjectReference` — the

No test defect was found beyond the one misclassified header line. Nothing was weakened.

## Scaffold added (phase 2)

All in the library, all compile-enabling only — no stub actually needed a `NotImplementedException`
body, because every new item is a data carrier rather than behavior.

| Item | Where | Shape |
|---|---|---|
| `XisfRawProperty` | `Models.cs` | `sealed record XisfRawProperty(string Id, XElement Element) : XisfProperty(Id)` — A6 exactly |
| `XisfHeader.UnknownElements` | `Models.cs` | `IReadOnlyList<XElement> { get; init; } = Array.Empty<XElement>()` |
| `XisfImage.UnknownElements` | `Models.cs` | same |
| `XisfMetadata` Rev-1 fields | `Models.cs` | four optional trailing positional params: `ushort? BlockAlignmentSize`, `string? ChecksumAlgorithms`, `ushort? MaxInlineBlockSize`, `string? OutputHints` — A7 |
| `XisfUnsupportedObjectException` | new `Exceptions.cs` | `sealed class : Exception`, message and message+inner constructors |
| `using System.Xml.Linq;` | `Models.cs` | required by the two new members above |

**Scaffold decision where the contract left room** — `UnknownElements` is a body-declared init-only
property, *not* a new positional constructor parameter. The contract said "least-invasive … optional
init/constructor params that don't break existing call sites"; a positional parameter would have had
to be `IReadOnlyList<XElement>?` (so the default could be `null`), and every test calls
`.Where(...)` on it unguarded. The body-declared form gives a non-null empty default, leaves every
existing `new XisfHeader(...)` / `new XisfImage(...)` call site and every `with` expression untouched,
participates in record equality, and lets wave 3 populate it with `header with { UnknownElements = … }`.

The four metadata fields *are* positional (A7 explicitly frees the order and the tests pass them by
name), appended after `RelatedResources` so no positional call site moves.

## Infra applied

- `XisfLib.Core.csproj`: added `<Compile Remove="Tests/**" />` + `<None Remove="Tests/**" />`
  (without this the root build compiles the test sources into the shipped library), and bumped
  `VersionPrefix` **1.2 → 1.3**.
- `.github/workflows/publish.yml`: a `Test` step between `Build` and `Pack` running
  `dotnet test Tests/XisfLib.Core.Tests.csproj -c Release -p:Version=<computed>`. The test project is
  not part of the root build, so this step restores and builds it itself.
  **Deviation worth flagging:** the contract's step text carried no `-p:Version`. Without it the test
  step rebuilds the referenced library *unversioned*, and the following `dotnet pack --no-build` would
  then pack a 1.3.0-stamped assembly inside a 1.3.`<run>` package. Passing the same computed version
  through keeps the library build identical to the `Build` step. Harmless on the test project itself
  (`IsPackable=false`).
- `README.md`: the data-types line now reads "IEEE 754 floats (32/64-bit)" (`XisfSampleFormat` has no
  128-bit member), plus a new **Support notes** section stating that property format specifiers are
  not applied — a `format` attribute is carried verbatim and never used to render or parse a value.

## What wave 3 must know that the table below does not carry

1. **Three greens pass vacuously today** and must be kept honest as the implementation lands:
   - `ValidationTests.NamespacedPropertyId_IsAccepted` and `SimplePropertyId_IsAccepted` pass only
     because `ValidateUnit` never reaches `ValidateImage` (`Validation.cs:74-97` ignores
     `unit.Images`). The moment A2 wires `ValidateImage` in, they hold **only** with the corrected
     single-colon `PropertyIdRegex`. Wiring the call without fixing the regex turns them red — and
     that pairing is the whole point of them.
   - `ByteOrderTests.Read_BigEndianEightBitImage_IsNoOp` passes because `byteOrder` is never parsed
     at all. After item 4 it must pass for the right reason: §10.4 makes endianness immaterial at
     item size 1.
2. **Contract item 14 needs no code change.** `CompressionTests.Read_ShuffledBlock_WithTail_...` is
   green across all four tail cases (18/4, 34/4, 36/8, 50/8), and
   `Write_ShuffledCodec_StoredBytesMatchSpecShuffleLayout` is green for item sizes 2/4/8 — so
   `ApplyByteShuffle`/`RemoveByteShuffle` already implement the §10.6.2 tail rule correctly. Item 14
   is a verify-only item and the verification passed. Do not "fix" that code; do keep the invariant
   when A10 moves shuffling to a single owner.
3. **A10 is not yet a live bug.** The monolithic writer never calls
   `DataBlockProcessor.WriteDataBlockAsync`, so today only `CompressionProvider.CompressAsync`
   shuffles and the codec round-trips are green. The double-shuffle becomes real the moment the
   item-9 write restructure routes blocks through the processor — pick the single owner *before*
   that, or `RoundTrip_EveryCodec_PreservesPixelData` (8 cases) and
   `RoundTrip_ShuffledCodecs_EveryItemSize` (12 cases) go red together.
4. **Two checksum tests are a matched pair and both must stay green.**
   `Read_CompressedBlock_BadChecksum_FailsBeforeDecompression` asserts the surfaced error message
   *contains* "checksum"; its control
   `Read_CompressedBlock_GoodChecksumOverInvalidZlib_FailsInDecompression` asserts the decompression
   failure's message *does not*. Wave 3 must not put the word "checksum" into any decompression
   error text, and must not drop it from the verification failure.
5. **A12 in one sentence, confirmed by measurement.** `PreservationTests.UnrecognizedContent_DoesNot
   ThrowOnWrite` is green *while the writer emits a bogus `<Reference ref="" />` root element* for
   each mangled unsupported core element. The sibling
   `UnsupportedCoreElement_NotMangledIntoEmptyReference` is the red test that catches it. Remove the
   uid-gated `XisfReference("")` mangling (`XmlSerializer.cs:337-340`) and the compensating
   write-side skip (`XmlSerializer.cs:576-578`) together, or preservation will double-emit.
6. **`PreservationTests` shape comparison is strict about attributes.**
   `HeaderProbe.AssertSameShape` compares *every* non-namespace attribute and the character content,
   recursively. So `UnrecognizedPropertyType_ReEmittedWithAttributesAndContent` requires the raw
   property to be re-emitted with its `length` and `location` attributes intact, not just `id`/`type`
   — `XisfRawProperty` must carry the element, not a reconstruction of it.
7. **`Assert.ThrowsAsync<T>` is exact-type.** `XisfUnsupportedObjectException` must be thrown as
   itself, not as a subclass and not wrapped, at the three sites that expect it
   (`ChecksumTests.Read_Sha3Checksum_...`, `DataBlockLocationTests.Read_UnknownCodec_Materializing...`).
   Likewise `LegacyCompatTests.VersionAttribute_MustBe10` pins `FormatException` exactly for a
   version that is not `1.0`.
8. **Read-side failure shapes that are currently green must not regress into A5's new path**:
   `Read_CorruptedStoredBytes_ThrowsInvalidDataException` and
   `NinaStyle_TamperedBlockFailsChecksum` both pin `InvalidDataException` for a *mismatch* — only the
   uncomputable-algorithm and unknown-codec cases become `XisfUnsupportedObjectException`.
9. **A14 stays untouched.** `XisfReaderOptions.FileStreamProvider`/`UriStreamProvider` remain ignored
   at `ComponentFactory.cs:50`; no test in this suite exercises them, so nothing forces the fix and
   nothing should tempt it.

### Where the implementation deviated from the contract's sketch

Each is minor and local; none changes what a test asserts.

1. **A10 — single shuffle owner is `DataBlockProcessor`, not `CompressionProvider`** (the contract
   "recommended" the provider). Subblocked writing has to shuffle the *whole* block, split, then
   compress each piece, which the provider's per-payload API cannot express. `ICompressionProvider`
   is now codec-only (`Compress(data, codec)` / `Decompress(data, codec, uncompressedSize)`) and
   `IDataBlockProcessor` owns `CompressBlock` / `DecompressBlock`, which apply and remove shuffling
   exactly once on both sides. `DataBlockProcessor.WriteDataBlockAsync`'s second shuffle is gone.
2. **A11 — the read path still hands back a materialized block with `Compression`/`Checksum` null.**
   Re-reading the anchors the contract cites (`XisfWriter.cs:198,244`), the drop item 9 must fix is
   the *writer's*: its temporary and final `AttachedDataBlock`s were built without the checksum.
   That is fixed. Carrying the stored-bytes `Compression`/`Checksum` onto the `InlineDataBlock` the
   reader returns was rejected: that block's `Data` is already decompressed, so the record would
   describe bytes that are no longer there and a second `ReadDataBlock` over it would decompress
   twice. A4 covers the read-modify-write intent case — a block that *does* carry a compression
   record governs the write, and `Options.DefaultCompression` applies only to blocks that carry none.
3. **Carrier for the unsupported-object policy (A5 / item 10).** Rather than add an
   `XisfCompressionCodec.Unsupported` member or a second codec field, `XisfDataBlock` gained one
   body-declared init-only property, `UnsupportedDeclaration` — an additive change that moves no
   call site, survives `with`, and covers the unknown-codec and unknown-algorithm cases uniformly.
   `ParseCompression`/`ParseChecksum` return `(value, unsupported)` instead of throwing, and
   `DataBlockProcessor` raises `XisfUnsupportedObjectException` at materialization. **Consequence,
   recorded:** an unknown codec's `compression` attribute is not re-emitted on write. Such a block
   cannot be materialized, so it cannot reach the writer through the normal path.
4. **A13 needed a synchronous read path.** The block-backed property pathway lives inside the
   synchronous `DeserializeProperty`, so `IDataBlockProcessor` gained `ReadDataBlock(block, source,
   options, itemSize)` and `ICompressionProvider`'s `CompressAsync`/`DecompressAsync` (whose only
   asynchrony was a `Task.Yield()`) were replaced by their synchronous forms — sync-over-async there
   would risk deadlock in a hosted context. `ReadDataBlockAsync` survives for the image path and
   remains the only route that can fetch a `url(...)` block. Both storage strategies pass an
   `XisfBlockReader` delegate into `DeserializeImage`/`DeserializeProperty`.
5. **Block-backed `String` property values are read** (§11.4.2's own `XISF:Description` example uses
   `location="attachment:…"`). No test requires it; it is five lines, gated on the presence of a
   `location` attribute, and without it such a property would silently read as empty.
6. **Byte-order item size for the complex sample formats** uses the component width (4 / 8), not the
   whole sample, per §10.4's "ordered multibyte subsequences". `Storage.ByteOrderItemSize`.
7. **The non-finite parser also accepts `Infinity` / `-Infinity`** beyond the §8.3.3 grammar, so
   files this library wrote before 1.3 keep reading. Emission is canonical-only (`NaN`/`+Inf`/`-Inf`).

### Emitted-bytes changes (the deliberate release delta, A3's journal line)

Four things about a file written by this build differ from 1.2, none of them API-visible:

- every element is in `http://www.pixinsight.com/xisf` (item 8; the reader still accepts bare names);
- `String` properties, metadata included, carry their value as character data, never a `value`
  attribute (A1);
- the `compression` attribute has two components for `zlib`/`lz4`/`lz4hc`/`zstd` and three only for
  the `+sh` codecs (A3);
- a `checksum` attribute appears when `XisfWriterOptions.CalculateChecksums` is set (item 9). The
  option's default is unchanged, so the default output gains no checksum.
